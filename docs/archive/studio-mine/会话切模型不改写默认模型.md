## 改动

两侧修同一件事：会话里换模型不再悄悄改掉「默认模型」。

- **内核侧**（`fd4e0e104`）：`POST /model` 请求带**显式 `default` 标志**——只有设置页的默认模型行与首次运行的模型选择才发 `default`；输入框旁的 picker 不发，只影响当前会话；走 hub resolver 的 pane 依旧不写本机配置。
- **界面侧**（`c4e755934`）：设置页「默认模型」行改绑后端 `GET /models` 已返回的"被标为 default 的条目"，不再跟 `status.modelRef`（当前会话模型）走。

## 动机

内核侧：`POST /model` 把**每一次**模型切换都持久化成"用户的默认模型"，于是"在某个会话里换个模型"会改掉所有新会话与下次启动用的模型；而打字 `/model` 命令、TUI、ACP 都不这么做——只有 HTTP picker 这条路径如此，属**路径间行为不一致**。

界面侧：设置页那行绑的是当前会话模型，会话里一换模型它就跟着动，看起来就像"默认值被改了"，把困惑放大一层。

## 取舍

- **请求带显式 `default` 标志**，而非在后端猜意图——只有默认模型行与首次运行才发，语义清晰。
- **界面侧只改取数**：后端早就返回了"被标为 default 的条目"，前端直接取用（`Settings.tsx` 一行未改）——**不新增接口、不引入第二个真源**。
- **内核那条 cherry-pick 上游修法**（上游 PR #11897），避免两线在这件事上行为分叉。

serve 的 `/model` 处理与 resume / settings、CLI、boot 的 `resume_model`；前端 `Settings` / `ModelUsage` / `Onboarding` 与 port 三处。
