# fork 三线并存维护（都不删、不冻结）

## 背景

上游 `esengine/DeepSeek-Reasonix` 于 2026-08-12 分成两条官方线：`studio`（2.x，默认分支）与 `main-v2`（1.x）。fork 侧同时还在自用旧版 Wails 体系（`v1.38.40`），需要在三套体系间取舍：是统一到一条线、还是让多条并存。

三线各有独立发版链与打包体系（Wails+NSIS / Electron），应用数据根天然分离，共享面只有项目内 `.reasonix/` 与 `~/.reasonix/locks`。

## 决策

**三条线并存、都不删、不冻结**：

- `wails-mine`（主用，旧版 Wails/WebView2 体系）——日常主力并持续修复；
- `main-v2-mine`（1.x 转 Electron 后那条线）——低频维护，需要时继续开发；
- `studio-mine`（2.x 主线）——Studio 有问题就在这条线修，等它稳定后再把主用迁过去。

`main-v2` 只作 1.38.x 的发布点（只读，不再新增 tag）。

## 理由

- 三套体系**各有独立发版链**，tag 触发的打包 workflow 天然按线隔离（tag push 时 GitHub 只用该 tag 指向 commit 里的 workflow 版本），并存不会互相触发。
- 已完成阶段 1-3 实施，配置落地可行（含各线 ci/release workflow 定制）。

## 备选与否决

- **统一到单线**：未采纳——三条线服务不同使用场景（日常主用 / 低频待续 / 主线跟进），合并会丢失其一。
- **冻结低频线**：未采纳——明确"都不冻结"，保留随时续开发的能力。

> 方案原文未记录更早备选讨论；如需补充请回填本栏。

## 影响

- 每线各自维护一份发版链（同名文件、内容按线定制），改 workflow 需注意线归属。
- 各类纪律（worktree、预检命令、发版流程）按线细化，固化在 skill `reasonix-flow`。
