## 1. 移植的第一原则：不要碰"两边共享的面"

两边并用时，下列是**共享**的（动了就会互相影响）：

| 共享面 | 说明 | 移植禁忌 |
|---|---|---|
| 会话文件与其格式 | wails 写 schema1/schema2/DAG 多代格式；studio 统一格式并**只读**导入旧格式 | **绝不能改会话写入格式或路径** |
| `%APPDATA%\reasonix` 下的配置/密钥/技能/记忆 | 两边同源 | 不改语义，只增不改 |
| 项目内 `.reasonix/`、`REASONIX.md`/`AGENTS.md` | 两边都读 | 不改解析语义 |
| 权限规则的表达（allow/ask/deny） | 两边语法同源 | 保持同源，不要单边改语法 |
| MCP / 技能 / hook 的加载与安装 | 两边共享配置 | 改动会影响 studio 侧行为 |

**判据**：一个移植如果**新增**能力、且**只读或只写自己的私有数据** → 安全；如果改了共享数据的**格式或语义** → 危险（会引入"两边行为不一致"的麻烦）。

## 3. 推荐的移植清单（按性价比排序）

### 3.1 「折叠可寻址」的前提核对（2026-10-06 深入核实）

**问题**：wails 有日志重写/轮转（`internal/agent/session_dag_rotate.go`），那 studio 的"按编号取回折叠内容"在 wails 上还成立吗？

**先看 studio 的寻址机制**（`internal/runtime/agent/compact_index.go` + `compact_recall.go`）：

- 索引段落标题字面量：`## Folded work index (#n = transcript position)`（`compact_index.go:indexSectionHeading`）
- `#n` 就是**规范化 transcript 的数组下标**（`recallSpan(canonical, pos)` 直接 `canonical[pos]`）
- 有效范围由 `CoveredCount` 界定：`pos >= covered` 时明确报错"还没被折叠，仍在你上下文里，直接读那里"
- 幂等：同一个 `#n` 再取一次，结果相同
- 索引里还给每条折叠项标了 `Kind`（you / 工具名）、`Note`（summary only / failed）——**摘要与索引互补**，不是互相替代（`compact_coverage.go` 负责划界）
- 回读进入上下文的形式是"普通工具结果"，**不是投影**，所以不破坏缓存前缀
- 能力开关：搜索折叠区可被配置关闭（ablation），关闭时错误提示会引导改用 `#n` 地址

**再看 wails 轮转的语义**（`session_dag_rotate.go`，注释即契约）：

> `rotateSessionDAG` 原子地把日志替换为下一代：**live heads 及其链保留它们的 id**、补丁被折叠、抹除物理生效、**一切不可达的被丢弃**。

- 触发条件（`save_dag.go:335` 是它的反向判断）：显式 rewrite-compact 模式、日志存在 holes、日志超尺寸 —— 三者之一
- 前置条件（`sessionDAGSingleWriterProof`）：本进程持租约 + 无交接预留 + **其他写者 60 秒静默期**
- 不满足就**拒绝轮转**，日志继续增长（`SessionRotationDeniedError`）

**结论**：

| 维度 | 判断 |
|---|---|
| 轮转会不会"重排"存活内容 | **不会**——被保留的（从 live head 可达的）内容保持顺序与数量 |
| 轮转会丢弃什么 | 只有**不可达**的条目（被取代的分支/悬空链） |
| 会话文件重写会不会影响当前会话的取回 | **不会**——取回读的是**内存中的规范化 transcript**，与磁盘日志是两套东西 |
| 那真实风险是什么 | **`#n` 是"位置"不是"身份"**：跨会话重启/切换后（磁盘重载 + 压缩重算）位置可能整体平移，导致旧索引里的编号指到别处 |

**风险的性质**：这是**失效（指错），不是崩溃**——位置越界会明确报错，落在范围内但有偏移则可能取回相近但不精确的内容。

**两条缓解路线（供实施选择）**：

| 方案 | 做法 | 成本 | 说明 |
|---|---|---|---|
| A（推荐，与 studio 一致） | 沿用位置坐标：索引在同一次压缩周期内生成并使用；跨重启后索引随摘要一起重建 | 中 | studio 正是这么做的——每代（generation）重建索引，`RecallLedger` 按代记账 |
| B（更稳但偏离 studio） | 给 `#n` 附加**消息 id（或内容哈希前缀）**，取回时校验 | 中高 | 需要 wails 侧确保消息 id 稳定；你已有 `Message.ID`（`ac0d22c59`），基础具备 |

**推荐**：先按方案 A 做，因为 wails 的 canonical transcript 本身就是**不可变、追加式**的（`agent.go:398` 注释："Context management keeps the canonical transcript immutable"），位置在"同一会话生命周期内"天然稳定；跨重启的偏移风险用"索引随摘要同代重建"消解即可。

#### §3.1.1 实证（2026-10-09，d--services 项目真实会话）

取 `d:/services` 项目下的真实会话 `20261008-052857…-axon-deepseek-flash`（用户主用线，多次压缩）：

## 4. "两边并用"要守的纪律（与移植无关但同样重要）

1. **同一项目同时只被一版打开**（项目内 `.reasonix/` 是共享写面）
2. 移植**只允许改 wails 线内部机制**，不允许改共享数据的格式或语义
3. 移植项要在 `docs/DeepSeek-Reasonix/changes/wails-mine/` 记决策（动机、取舍、回退）
4. 每移植一项 = 一份长期自维护成本（wails 线无上游供血）；**建议最多挑 1~2 项**（首选"折叠可寻址"）
