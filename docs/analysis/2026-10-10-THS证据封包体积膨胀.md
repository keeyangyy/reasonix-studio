# THS 证据封包体积膨胀（`trusted/` 无上限增长）

> 调研日期 2026-10-10 · 实测环境 Studio 2.x（studio 线，上游 base 2.34.0）· Windows 11 amd64
> 起因：Studio「存储」面板显示「配置与凭据 3.7 GB / 90399 个文件」，排查这是什么、为什么越来越大。

## 结论摘要

1. **大头是 `%APPDATA%\reasonix\trusted\`**（THS 可信执行层），实测 **2634.9 MB / 73955 个文件**，占整个数据根（3794.7 MB）的 **69%**。
2. **它无上限增长**：存储层只有 `Append`，**没有任何回收**（无 `Delete/Prune/GC/Trim`）。近 10 天每天新增 0.1–0.5 GB，只增不减。
3. **体积的真正来源不是工作区快照，是 `criteria` 列表**：每轮 bundle 里内联 13474 条验收标准（每条含测试文件**绝对路径**，平均 191 字节），并被 `verdict.obligations` 再镜像 13478 条。
4. **面板「配置与凭据」这一栏名不符实 + 与「会话与归档」重复计数**——同一批 `trusted/` 数据被算了两次。
5. **不能当缓存直接清**：它在运行路径上被**读回**（跨进程恢复契约、每轮回看上一轮快照），删掉会丢契约续跑基准。详见 §4。
6. **上游已于 10-10 自行修复写入放大**（PR #12609，进 `v2.35.0`）：bundle 不再内联 criteria/obligations，每轮从 10.1 MB 降到 KB 级。**但①没有回收存量；②修复不完整**——`contract/1` 契约记录仍内联全量 criteria，每开新任务仍写约 4.5 MB。本机 Studio 已是 **2.35.0**（10-11 14:51 装好），**清理不必再等升级**。详见 §7。

## 2. 它是什么

**THS = Trusted Host State（可信执行层）**，定义在 `internal/state/trustedstate/doc.go`：
内容寻址对象（objects）+ 每个工作区一条哈希链（streams），链头 `HEAD` 指向最新记录。

**写入时机**：每轮对话结束（`internal/runtime/agent/evidence_seal.go` 的 `sealShadowBundle`），
把这一轮的 `shadow_bundle/1` 追加进该工作区的链：

```jsonc
{
  "kind": "shadow_bundle/1",
  "input_digest": "<本轮输入的 sha256>",
  "contract":     { ... },        // 任务契约摘要
  "report":       { ... },        // 模型自称的完成情况
  "receipts":     [ ... ],        // 每次工具调用的回执（参数只留 digest）
  "criteria":     [ ... ],        // 这一轮的任务契约要求
  "task_contract":{ ... },        // ← 契约完整快照（体积大头之一）
  "verdict":      { ... },        // ← 宿主裁断 + obligations（体积大头之二）
  "snapshot_before": { ... },     // 轮次开始时的全工作区目录树快照
  "snapshot_after":  { ... }      // 轮次结束时的快照
}
```

另有 `contract/1` 记录（`internal/runtime/contract/store.go`，同一条 stream）承载契约修订。

## 3. 为什么这么大（代码定位）

### 3.1 直接原因：`criteria` 列表被内联进每轮 bundle

解剖最大的那个对象（10.11 MB）得到的字段构成：

| 字段 | 大小 | 内容 |
|---|---|---|
| `task_contract.criteria` | **6537 KB** | **13474 条** |
| `verdict.obligations` | **3994 KB** | **13478 条** |
| `receipts` | 64.8 KB | 118 条 |
| `contract`（摘要） | 5.4 KB | — |
| `criteria`（顶层） | 1.3 KB | — |
| `snapshot_before` / `snapshot_after` | **各 0.2 KB** | ← 工作区快照本身极小 |

每条 criteria 长这样（**平均 191 字节**，`sum(id len)` = 2583612）：

```json
{"id":"test@baseline_test@<workspace>\benchmarks\e2e\tasks\<case>\workdir\...\order_test.go@sha256:<64hex>",
 "source":"baseline_test","required":true,
 "verifier":{"kind":"test","identity":"baseline_test@<同上>"}}
```

### 3.2 溯源链

```
captureCriteriaUnder(a.writeWorkspaceRoot)              baseline_criteria.go:116
  └─ filepath.WalkDir 遍历整个可写工作区
       └─ captureCriterionAt(path)                       baseline_criteria.go:148
            ├─ evidence.PathMayHoldTestCriteria(path)    = 后缀 "_test.go"  (test_criteria.go:16)
            └─ evidence.HoldsTestCriteria(path, content) = 能解析出 Test/Benchmark/Fuzz/Example
                 └─ store.Capture(path, content)
                      └─ TestCriterion{LogicalID: path, Digest: sha256}   testcriteria.go:57
                           └─ Identity() = "baseline_test@" + LogicalID + "@" + Digest   testcriteria.go:27
                                └─ 逻辑 ID = 测试文件的【绝对路径】

a.baselineTestIdentities()                              task_contract.go:84
  └─ contract.Derive(Sources{Tests: ...})               contract.go:91
       └─ Criterion{ID: "test@" + id, Source: baseline_test, Verifier.Kind: test}   contract.go:84
            └─ 整个 criteria 数组进 bundle 的 task_contract   evidence_seal.go:109
                 └─ verdict.Evaluate 再镜像一份进 obligations  verdict.go
```

### 3.3 为什么会被放大

三个乘数叠在一起：

1. **按测试文件数放大**：扫描面是**整个可写工作区**下所有 `*_test.go`，每个 `Test/Benchmark/Fuzz/Example` 函数算一条。
   本项目有 `benchmarks/e2e/tasks/**`（大量独立 Go module 的测试）、`desktop/third_party/go-webview2`
   等第三方目录，全部计入。
2. **按路径长度放大**：ID 里带**绝对路径**，路径越长越多条目越大。多个 worktree
   （`worktree/DeepSeek-Reasonix-*`）会让同一份测试代码在不同工作区各记一遍、且路径更长。
3. **按轮数放大且去重失效**：bundle 每轮整份重写，payload 因 `revision`/`verdict`/`epoch` 变化
   而每轮字节不同 → 内容寻址存储的去重**完全不生效**，同一批不变内容被反复整份落盘。

### 3.4 为什么不会变小

`internal/state/trustedstate/` 全包方法清单（`store.go` + `objects.go`）：

```
Append  Head  Record  Verify  Root  Object  PutObject  PutIndexObject
streamDir  head  consistentWithObserved  observedHead  observe
objectPath  checkObjectFile  putObject  writeFileAtomic  writeFilePublished
DigestOf  hex  FailureCode  Open
```

**没有 `Delete` / `Remove` / `Prune` / `GC` / `Trim` / `Compact`**，`criteria` 列表也没有条数上限。
唯一的 `os.Remove` 在 `objects.go:129`，是临时文件的 `defer` 清理，与回收无关。
对象设计上就是 immutable（按内容寻址、只增不改）。

## 4. 读回路径（决定"能不能删"）

⚠️ **重要更正**：`evidence_seal.go:30` 的注释 `The bundle observes and gates nothing`
容易让人以为整个存储只写不读——**那是 `shadow_bundle` 这一条记录的性质，不是整个存储的性质**。
实测（codebase-memory-mcp 图谱 + 源码核对）存在这些**运行路径上的读取**：

| 读操作 | 位置 | 用途 | 时机 |
|---|---|---|---|
| `Store.Head` | `turn_snapshot.go:87` | 读链头做防回滚比对 | 每轮 |
| `Store.Record` | `turn_snapshot.go:91,93` | 沿链回退找上一轮 bundle（`maxRecordsBack=8`） | 每轮 |
| `Store.Object` | `turn_snapshot.go:98` | 读上一轮的 workspace 快照 | 每轮 |
| `contract.Load` → `Record`+`Object` | `contract/store.go:25`；经 `task_contract.go:59 的 contractInForce` | **读回上一版任务契约** | 跨进程恢复 |
| `Store.Head`（防回滚） | `store.go:167,203 consistentWithObserved` | 拒绝被改写的链头 | 每次 Append |

`task_contract.go:56` 注释说明了它的核心价值：

> The cached copy is trusted only while it is the one named... **read back from Trusted Host State
> rather than re-derived from what it reads now**

即：跨进程恢复（`/goal` 续跑、重启继续）时契约是**从 THS 读回**的，不是重新推导——这样"上一版
接受了什么验收标准"无法被事后改变。`internal/session/control/goal_resume_contract_test.go` 专测此场景。

**推论**：
- 没有 `/goal` 类跨会话长任务在跑时，删 `trusted/` 影响很小（下次对话会在同位置重建链）。
- 有任务在续跑时删掉，会因读不到上一版契约而按失败处理（`task_contract.go:28` 注释明确
  不接受"用一个新契约顶替"）。
- 要回收的话**整目录一起清**（不能只删部分对象，会让哈希链悬空），走 `trash` 送回收站。

## 5. 面板口径陷阱（「配置与凭据 3.7 GB」的由来）

截图那五行来自 `desktop/frontend-next/src/ui/Storage.tsx`，行名在本文件 `NAMED`：

| 面板行 | root id | 实际统计范围 |
|---|---|---|
| 配置与凭据 | `home` | **整个 `%APPDATA%\reasonix`** |
| 会话与归档 | `state` | 同目录下**指定的那些条目**（`StateRootEntries`） |
| 索引与缓存 | `cache` | `%LOCALAPPDATA%\reasonix` |
| 隔离工作区 | `worktrees` | checkouts |
| 进程锁 | `locks` | 空文件 |

实测对账（`internal/contract/config/storage_roots.go` + `internal/state/storage/survey.go`）：

| 面板行 | 实测 |
|---|---|
| 配置与凭据 `home` | 3794.7 MB / 90426 |
| 会话与归档 `state`（= `StateRootEntries` 之和） | 3675.9 MB / 89842 |
| 索引与缓存 `cache` | 844.6 MB / 8215 |

两个坑：

1. **同目录被算两次**。Windows 默认安装下 `state` 根就落在 `home` 根
   （`storage_roots.go:284 defaultStateDir() = Dir(RootHome)`）。区别只在 `measureOwned`
   按 `RootOwns` 过滤：`home` 无 `owns` → 统计整个目录；`state` 有 `owns` → 只统计声明条目。
   **而 `trusted` 恰好在 `StateRootEntries` 里**（`storage_roots.go:176`），于是
   home 那行按"整目录"算了一遍，state 那行又按"声明条目"算了一遍——两行都 3.x GB，
   加起来像 7 GB，实际是同一批 ~3.8 GB。
2. **「配置与凭据」名不符实**。该行提示语是「设置与 API key，始终随用户配置文件保存」，
   但它统计整个目录，其中 2.6 GB 是证据快照。用户从这里查"为什么这么大"会被名字误导。

> ⚠️ **路径易错**：`objectPath` = `objects/<digest前2位>/<**完整**64位hex>`（`objects.go:42`），
> 文件名是**完整的** 64 位，不是"去掉前 2 位"。按"去掉前2位"去查会全部报缺文件，误判成链断裂。
> 实测文件名校验：`objects/13/` 下 276 个文件，文件名长度**全为 64**。

## 8. 下次怎么快速复现

1. **统计占用**（递归合计，注意 `trusted/` 是 7 万+ 小文件，慢）：按目录 `os.walk` 累加
   `st_size` 与文件数即可；`objects/` 再按大小分档看集中度。
2. **看增长**：按 `st_mtime` 分日汇总 `objects/` 的字节与文件数——能直接看出"每天涨多少"。
3. **看单对象构成**：取 `objects/` 里最大的几个，直接 `json.load` 后按顶层 key
   逐字段 `len(json.dumps(v))` 排序，即可一眼看出是哪个字段在撑体积。
4. **看读回路径**：改动前先确认是否有运行路径读取，别被 `observe and gates nothing` 这类
   单条记录的注释误导（见 §4）；用 `codebase-memory-mcp` 的 `search_graph(include_connected)`
   查方法的 `connected` 列表最省事。
