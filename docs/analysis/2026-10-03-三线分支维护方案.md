## 4. 各线流程

### 4.1 `wails-mine`（主用线）

- 预检：`go run ./tools/repolint`、`gofmt -l <改动go文件>`、`cd desktop && go test .`（嵌套模块，父模块 `go test ./...` 看不到）、前端 `cd desktop/frontend && npx -y pnpm@10 install --frozen-lockfile && npx -y pnpm@10 build`
- 本地出包：先 `npx -y pnpm@10 build` 构建前端，再 `cd desktop && wails build -s -ldflags "-X main.version=<ver>"`；完整包走 `bash scripts/desktop-build.sh windows/amd64 <ver>`
- 发版：`gh workflow run "Release (manual)" -R keeyangyy/DeepSeek-Reasonix -r wails-mine -f version=1.38.41`（version 不带 `v`）→ 等 CI 绿 → 打 tag `v1.38.41` → draft Release → `release-windows.yml` 出便携包 + NSIS 安装包
- 产物：`Reasonix-windows-amd64-<ver>.zip` + `Reasonix-windows-amd64-installer-<ver>.exe`
- 注意：`wails build` 默认会调用系统 `pnpm`（本机 11 违规），必须先用 `npx -y pnpm@10` 构建前端，再 `wails build -s` 跳过前端步骤

## 5. CI 改造清单（已实施）

每条线只认自己的三件套，互不引用：

1. `ci.yml`（以及 `app-memory` / `cache-impact` / `docs-impact` / `codeql` 的触发段）：`branches` = 本线
2. `release-manual.yml`：等待本线 CI 绿 + `ref:` 本线 + `gh release --target` 本线 + dispatch 打包时 `--ref` 本线
3. `release-windows.yml`：tag 形状校验 + **tag 必须位于 `origin/<本线>`**（三条线都已具备）

**有意保留原样的两点**：
- **workflow 的 `name:` 不改**（三线都叫 `Release (manual)` / `Release Windows`）：`gh workflow run` 靠 `-r <分支>` 选中本线文件，改名反而会让既有命令与文档全部失效；Actions 列表里用分支字段区分即可。
- `scripts/check-cache-impact.sh` / `check-docs-impact.sh` 的 fallback base 仍写 `origin/main-v2`：它指向本线起点（= `v1.38.40`），语义仍正确。

## 6. 共存纪律

- 同一项目目录**同一时间只被一版应用打开**（项目内 `.reasonix/` 是两版共享的写面）；
- 两版数据根天然分离，可同机并存、独立升级，互不覆盖；
- **不加额外隔离**（不设独立 `REASONIX_HOME`），以纪律代替配置；

## 7. 改动联动

- **各线独立**：修复只落在本地线，不强制双写；确实多线都需要的（如内核 bug）**手动 port**，与过去的 `main-v2 → main-mine` 搬运方式一致；
- 迁移方向只有一条：`wails-mine` 的成果将来人工 port 到 `studio-mine`。

## 12. CI 稳定性：诊断与改造（2026-10-03 下午）

### 现象
- `wails-mine`：`test (windows-latest)` 连续 attempt 1/2 失败（`internal/bot` runtime 崩溃、`internal/agent` 284s、`internal/control` 163s）
- `main-v2-mine`：先红在 `internal/provider` 的 HTTP2 时序测试 + lint（essay），后红在 `internal/plugin`（包级 8m 超时）
- `studio-mine`：同一个 run 需要 attempt 4 才绿

### 根因（三类，性质不同）
1. **环境性 flake（不可根治）**：Windows hosted runner 的 Go runtime/OS 层抖动（寄存器转储、`rip=0x0`；Defender 实时扫描与 Intel AMX 也会崩 Go 堆，见 golang/go#81238、#67139）+ 对时序敏感的测试。特征：**本机不复现**（HTTP2 那个 `-count=10` 全过）、重跑即绿、每次红在不同的包。
2. **机制缺陷（可根治）**：
	- `wails-mine` 的 `test (full)`：命中 flake 后的重试要重跑全量（11–12 分钟），而步骤预算只有 20 分钟 → **撞一次必然红**
	- `main-v2-mine`：`internal/plugin` 不在 `isolatedGroups` 里 → 混在 `full` 中抢资源，卡住即整包 8m 进程级超时；而该形态（`panic: test timed out after`）被 `KNOWN_RUNNER_FLAKES` 刻意排除（视为真 hang，不重试）
	- 三条线都缺「失败自动重跑」
3. **本次改造自己引入（已修）**：`GOMAXPROCS=2` 反而成为新崩溃点（`fatal error: fault` in `[GOMAXPROCS updater (idle)]`）；测试注释超 repolint 的 essay 3 行上限

### 改造（三线各自落地）
| 线 | 提交 | 内容 |
|---|---|---|
| `wails-mine` | `cb7944471`、`284b285f2`、`3dbabb90d`、`adda0286f` | 重试只跑失败包 + 预算 20→35；撤掉 GOMAXPROCS（`3dbabb90d`）；新增 `test (flake-prone packages)`（bot/plugin/agent 逐个跑、各自重试一次）；`test (full)` 用 `go list` 排除这 3 个包；job 预算 45→60；新增 `auto-rerun` |
| `main-v2-mine` | `d5001285e`、`82e9d1da9`、`4c5b4199c` | HTTP2 建连竞态修复（先发 SETTINGS → 等客户端 HEADERS → 再写非法帧，预算 5s→30s）；注释压到 3 行；`plugin` 并入 `isolatedGroups` 与 matrix；新增 `auto-rerun` |
| `studio-mine` | `c20a1cb44` | 新增 `auto-rerun`（该线尚未定位易崩包，先用自动重跑兜底） |

`auto-rerun` 三线统一语义：任一 job 失败时执行 `gh run rerun --failed`，仅在 `github.run_attempt == 1` 触发（不会循环）。

### 结论与后续
- 能根治的（机制缺陷）已修；不能根治的（Windows 环境抖动）靠「单包重试 + 自动重跑」消化
- 减少"推一次红一次"的关键在 **push 前的确定性预检**（repolint / gofmt / vet / 改动包测试 / 契约）→ 已固化进 `reasonix-flow` skill v0.5.0 的「push 前预检」章节
- 环境性 flake 不要试图本地复现：本机跑 Go 全量有大量环境性失败，以 CI 为准

## 13. CI 精简与提速（2026-10-03 晚）

### 判据：关键路径（最长 job）决定墙钟
| 线 | 优化前关键路径 | 优化后（预期） | 做了什么 |
|---|---|---|---|
| `wails-mine` | `desktop-windows` **32.8 min** | **实测**：`desktop-windows` **9.2 min**，新关键路径 `desktop-windows-go` **27.4 min**；该 run 墙钟 35.2 min | 把该 job 里的 Go 套件（`go test ./...` 单步 **23.4 min**）拆成独立 job `desktop-windows-go`，与 WebView2 冒烟并行；新 job 只需 checkout + Go，不需要 pnpm/前端构建 |
| `main-v2-mine` | `race` 13.8 min | ~14 min | 已是矩阵结构（`windows-isolated` 分区 + `desktop-windows-go-group`），关键路径未动 |
| `studio-mine` | `test (windows-latest)` 10.2 min | **实测 9.2 min**（run 墙钟 10.1 min） | 结构最简，未动 |

**拆分生效但收益被环境掩盖**：那一次 run 里 `test (windows-latest)` 也从 10.9 涨到 **19.5 min**（同一份代码），说明是 runner 整体偏慢，不是拆分导致；`desktop-windows` 从 32.8 → **9.2 min** 是拆分的直接效果。被拆出的 `desktop-windows-go` 里那 27.4 min 主要是 Windows 上重编 cgo/Wails 包（约 20 min）+ 主包 6.1 min 测试——**这是单个大包的硬成本，分片无法消除**（按测试名分片也要各编译一次该包），因此不再进一步分片。

那 23.4 min 的构成（实测）：Windows 上重编 cgo/Wails 包 + 主包 6.1 min 测试；setup-go 的 Go 构建缓存（`Cache restored from key: setup-go-Windows-x64-...`）已生效，剩余重编来自代码改动 —— 因此**分片不划算**（3 片各重编一次，反而 3× 成本）。

### 失败自动重跑（`ci-rerun.yml`）落地与验证
- 第一版做在 run 内 → GitHub 拒绝：`run ... cannot be rerun; This workflow is already running`，即 **run 不能在运行时 rerun 自己**
- 第二版：独立 workflow，`workflow_run`（CI completed）+ `workflow_dispatch` 手动兜底，`if: failure && run_attempt == 1`，动作 `gh run rerun --failed`
- **`workflow_run` 只有默认分支上的定义才生效**（当前 `wails-mine`）→ 那份文件实际是仓库级盯所有分支的 `CI`；三条线保留同名文件只为"跟随线走"
- 实测：`CI rerun` 出现 `success` 记录（11:00:21），`main-v2-mine` 被它推入 attempt 2 ✓

### 试过但回退的：删掉"与 Windows 无关的 job"
- 尝试删 `desktop-go` / `desktop-go-race` / `coverage` / `desktop-linux-webkit41` / `desktop-macos` / `site`
- **回退原因**：撞上游契约护栏（`ci-workflow.test.mjs` 断言「required aggregate 必须覆盖每个子 job」「每个 job 必须可达」），一次 9 条断言红；而这些 job 多在 ubuntu 上、与关键路径**并行** —— 删它们**不缩短 CI 时间**，只省额度
- 结论：**时间优化要动关键路径上最长的那个 job**；删 job 需同步改写上游护栏（并增加上游合并冲突），代价大于收益
